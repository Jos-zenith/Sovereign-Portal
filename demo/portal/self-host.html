Self-host अपना सर्वर

Free. Yours. In Mumbai.

There is no VICT cloud. You run it in your own AWS ap-south-1 account, so borrower data never passes through a third party, including us. No licence fee, no telemetry, nothing that phones home.

Where it stands. The core is built and tested: consent tokens, the egress proxy, the hash-chained ledger and the NBFC witness. Packaging them as separate production services is in progress, and design partners decide what comes first. What's left.
1

Run it on your laptop

The gateway, consent authority, proxy, ledger and witness all start in one process, with stand-in vendors. Point this site at it with ?api= and every page talks to your copy.

Works today.

Terminal
git clone https://github.com/Jos-zenith/Sovereign-Portal
cd Sovereign-Portal
python -m pip install -r src/requirements.txt
uvicorn src.gateway.consent_gateway:app --port 8080

# in a second terminal
python -m http.server 5500 --directory demo/portal
# open http://127.0.0.1:5500

Read the tests, then run them

The egress test suite is the specification: raw CONNECT requests for every block reason, bureau-style mTLS through the proxy, mid-stream withdrawal, audit-write failures, and a witness against an honest and a dishonest LSP.

Works today.

Terminal
python -m pip install -r requirements-dev.txt httpx
python -m pytest tests/egress -q
3

Lock down the network

Apply the egress_lockdown Terraform module to your app subnets, then run verify_lockdown.sh on an app instance. It doesn't read your configuration: it tries to get data out over HTTPS, raw IPs, IPv6, UDP DNS, another account's S3 bucket or queue, and internal relays, and writes down what actually happened in a JSON report you can hand to your NBFC.

Validated with offline Terraform tests. Not yet applied to a real AWS account.

Terminal
cd infra/terraform
terraform init
terraform plan -var="region=ap-south-1"

# on an app instance, after apply
./modules/egress_lockdown/verify_lockdown.sh <proxy>:3128
4

Hand your NBFC the witness

Give them your checkpoint public key and your gateway URL. They run one process on their side; it never receives borrower data.

Works today. What the NBFC sees.

At the NBFC
python -m src.egress.witness \
    --lsp-url https://vict.your-lsp.in \
    --lsp-id your-lsp \
    --public-key lsp-checkpoint.pub.pem \
    --state witness-state.json --interval 10

Before production

What's left to build.

Straight from the repository's production-readiness notes.

  • Consent authority as its own service. Today it runs inside the gateway. App code must never hold the token-signing key, and withdrawals need a push channel to the proxy.
  • Durable ledger storage. The demo writes to temporary files. An S3 bucket with Object Lock is the natural home.
  • Key management. Generate the checkpoint key at install, keep it in AWS KMS or Secrets Manager, and agree a rotation procedure with the NBFC.
  • NBFC counter-signatures, so the LSP also holds proof of what was witnessed.
  • A first run in a real AWS Mumbai account, with verify_lockdown.sh passing.

No fine print

Limits, stated up front.

  • Vendors' storage location. The allow-list controls hostnames, not data centres. A vendor's data residency is its contractual promise.
  • Erasure. Withdrawing consent stops future calls and cuts open ones. Erasing data a vendor already holds is still the lender's job; the ledger shows who received it.
  • Completeness. The NBFC witness proves witnessed history wasn't changed. Network lockdown is what makes an unlogged call hard to arrange.
  • DNS. Compromised code could leak small amounts of data through DNS lookups until DNS Firewall is turned on.
  • Withdrawals across services. They cut open connections within a second while the consent store runs inside the proxy's process. A separate consent service will need to push them.
  • Real bureaus and AAs. The public demo answers every vendor with a local stand-in.

Questions

Asked by LSP engineers.

Do you ever see our borrowers' data?
No. There is no hosted service and no telemetry. You run every component, and the NBFC's witness only receives hashes. The public demo uses stand-in vendors and made-up borrower IDs.
Does it replace our consent manager or Account Aggregator?
No. VICT enforces the consent you already collect at the moment data would leave your servers. It isn't a DPDP consent manager or an AA, and it works alongside both.
Will it slow down underwriting?
It adds one token request and one proxy handshake per vendor session, inside your own VPC. Ledger writes happen off the request path. The ledger handles about 3,000 entries per second on a laptop, against roughly 5 per second for 100,000 loan calls a day.
Which languages are supported?
There's a Python SDK today. The proxy speaks standard HTTPS CONNECT, so any client that supports a proxy can use it once the consent authority runs as its own service and hands out tokens over the network.
Does running VICT make us compliant?
No tool can promise that. VICT enforces and evidences specific obligations about outbound data, and the rule map says which ones. The rest of compliance is still yours.
