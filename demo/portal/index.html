Three parties एक बही

Three parties, one ledger.

A digital loan touches the borrower, the app that runs it and the NBFC that funds it. VICT gives each of them something they can check, instead of something they're told.

सहमति

Borrower

Says yes for one purpose, and can take it back.

  • Consent is per lender and per purpose. A loan check is not a marketing list.
  • Withdrawing cuts connections that are already open, within a second.
  • Every use of their data is a line in the ledger.
नियंत्रण

LSP · your loan app

Compliance lives in the network path, not a spreadsheet.

  • One SDK call wraps each vendor request.
  • Bureau mTLS and signed AA payloads pass through untouched.
  • A rogue SDK or a mistyped host is blocked on the spot, not found in an audit.
साक्ष्य

NBFC partner

Checks the LSP's log for itself.

  • Pulls a signed checkpoint every few seconds.
  • Receives hashes only, never borrower data.
  • Raises an alarm the moment history is rewritten.

Rejection slips

What a loan app actually gets caught doing.

Each slip is a real reason code the gateway writes to the ledger. None of them depends on the developer remembering a rule.

Blocked consent-record-not-found

Marketing reuses a loan consent

The borrower agreed to an eligibility check, not a cross-sell campaign. Purpose is part of the consent.

Stopped by: consent authority
Cut consent-withdrawn

Borrower says stop mid-fetch

A bank-statement pull already in flight is closed within a second of the withdrawal, not when a token runs out.

Stopped by: egress proxy
Blocked host-not-allow-listed

An SDK phones home abroad

An analytics library deep in your dependencies posts profile data to a server outside your vendor list.

Stopped by: egress proxy
Blocked host-not-in-token

Consent for one vendor, call to another

The token says "bureau". The code connects to the AA. Each token names the hosts it may reach.

Stopped by: egress proxy
Blocked raw-ip-target

Hard-coded IP to dodge the list

Connecting to an address instead of a name is refused outright.

Stopped by: egress proxy
Blocked token-bad-signature

The app writes its own consent

Only the consent authority holds the signing key. A token the app made up is rejected.

Stopped by: egress proxy
Blocked token-tunnel-limit

One leaked token, many connections

A token lives 60 seconds and opens at most four connections, so a leak can't fan out.

Stopped by: egress proxy
No route network lockdown

Code skips the proxy entirely

App subnets have no route to the internet except through the proxy. The one known gap is DNS lookups, until DNS Firewall is on.

Stopped by: AWS network rules

The 30-second version

Three checks, one log, one outside witness.

1

Ask before you send

Your code asks the consent authority for a token naming the borrower, the purpose and the vendor. No valid consent, no token, no network call.

2

Show the token at the gate

The egress proxy checks the token, the host and the port, then opens an encrypted tunnel it cannot read. The network closes the other routes out, except DNS until DNS Firewall is on.

3

Write it where the NBFC can see

Every decision is chained into a hash log. Your NBFC partner pulls signed checkpoints and gets an alarm if any witnessed history changes.

No fine print

What VICT won't do for you.

Compliance tools that claim everything are worse than none. Here are the gaps, stated up front.

Full list of limits
  • It can't make vendors delete data. Withdrawal stops future calls. Erasure of data a vendor already holds is still your job; the ledger shows who received it.
  • A hostname isn't a data centre. The allow-list controls which vendors you call, not where they store data. That part stays contractual.
  • The witness proves no rewrite, not completeness. It catches deleted or edited history. Network lockdown is what makes a missing record hard to arrange.
  • DNS can still leak a little. Closing it needs AWS DNS Firewall, which is a paid service.
